# Taste
- When generating deliverables (test plans, coverage verification reports, etc.), expects both a Markdown (.md) file and a PDF file as deliverables, saved into an output folder (explicitly restated in follow-up requests: "result should be in output folder with md and pdf file"). Confidence: 0.95
- Skill outputs must actually be written to files, not just summarized in chat — the user pushed back with "file not updated...update with new names which is KAN-3_verify-test-cases" when the verification report was only shown in the conversation. Uses the naming pattern `{TICKET}_verify-test-cases` for coverage verification report deliverables (e.g., `KAN-3_verify-test-cases.md` + `.pdf`). Confidence: 0.7
- Refers to Jira tickets by ID (e.g., KAN-2, KAN-3) when requesting test plans and expects the plan content to come from the actual ticket, not invented. Confidence: 0.9
- Expects JIRA credentials to be available in the project's `.env` file and directs the assistant to check there for ticket fetching, rather than asking interactively for credentials (repeatedly says "check .env file"). Note: the project's `.env` actually uses `JIRA_URL` and `JIRA_API_TOKEN` (not the skill's `JIRA_BASE_URL`/`JIRA_TOKEN`), so check for both naming conventions. Confidence: 0.85
- When reporting completed file deliverables, the user checks the output folder themselves and expects the assistant to verify the files actually exist and are valid (presence, size, %PDF header) and to state the exact full path — the user will push back ("pdf file not created") rather than trust a bare "done". Confidence: 0.6
- When executing a task tied to a specific skill, restricts the assistant to that skill's files only (e.g., only the test-case-generator SKILL.md) and does not allow reading other skills; the named skill file is the authoritative reference and should be re-checked rather than relying on memory. When content is contaminated by external references, the user demands a clean regeneration from scratch using only the skill + the actual source ticket (explicitly: "do not take any reference from the other skills or any other source. Do it again") — no other skills, no asset PDFs, no prior documents — and expects the final deliverables to be verified clean of the disallowed references. Confidence: 0.9
- Expects every claim in deliverables to be traceable to actual sources — the user will challenge ungrounded content (e.g., asked why a product was named "VWO (Wingify)" when they never wrote it). All inferences/assumptions must be explicitly flagged as unconfirmed and surfaced for user confirmation, never stated as fact. Confidence: 0.9
- Explicitly invokes an anti-hallucination rule for deliverables by pointing to the exact skill file that defines it (e.g., "use hallucination rule ...\\.github\\skills\\02-test-case-generator"). Applying it means: never invent ticket content, never fabricate acceptance criteria (a missing AC is a finding, not a blank to fill), keep every scenario traceable to a requirement or flagged gap, mark all unknowns as TBD/open questions, and keep the deliverable DRAFT pending a human review gate. Confidence: 0.8
- When producing PDF deliverables from markdown, renders the markdown to styled HTML first (so tables and formatting are preserved) and prints it with headless Chrome/Edge, matching the toolchain of existing PDFs — printing raw markdown as plain text is not acceptable. Confidence: 0.6
- Keeps the output folder clean: removes intermediate artifacts (e.g., the temporary HTML used for PDF generation) so only the final deliverables (`.md` + `.pdf`) remain per ticket, matching the established KAN-2/KAN-3 pattern. Confidence: 0.6
- Before committing, runs a pre-commit security check to verify no credentials leaked into the staged set: `git ls-files` filtered for env files, `git check-ignore .env`, and a review of `git diff --cached --name-status`; only then stages, commits, and pushes. Confidence: 0.6
